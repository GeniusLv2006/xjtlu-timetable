# Timetable Toolkit for XJTLU Students v0.3.0

v0.3.0 adds a restricted self-service path for selected suspended accounts and a privacy-preserving control against immediate re-registration after a suspended account is deleted.

## Highlights

- Let administrators choose between complete login denial and restricted account access when suspending a user.
- Limit restricted sessions to a dedicated page for complete data export, password-confirmed account deletion, legal notices, and sign-out.
- Enforce the restriction in PocketBase hooks, collection rules, token refresh, and frontend routing rather than relying on the user interface alone.
- Require the current password for every self-service account deletion.
- Block re-registration for a configured period after a suspended account is deleted without retaining the clear-text email address in the blocking collection.
- Rotate account-blocking HMAC keys without invalidating identifiers created with the previous key.

## Upgrade

Back up an existing v0.2.1 installation, configure the account-blocking key, and then run the supported upgrade command:

```bash
openssl rand -hex 32
# Store the output only in ACCOUNT_BLOCK_HMAC_KEYS in the private .env file.
./self-host.sh upgrade v0.3.0
```

The migration adds `users.restricted_login_allowed`, the server-only `blocked_registration_identifiers` collection, and `site_config.blocked_registration_retention_days`. Existing suspended accounts continue to receive complete login denial until an administrator explicitly enables restricted access.

`ACCOUNT_BLOCK_HMAC_KEYS` is required whenever blocked-registration retention is enabled. The first comma-separated key creates new HMAC-SHA256 identifiers; later keys allow matching identifiers created before rotation. Never commit, log, export, or expose populated key values to the frontend.

The default retention period is 365 days and can be changed from 1 to 3650 days. Setting it to `0` disables the control and removes existing blocking identifiers. Shortening the period shortens existing records; increasing it affects only identifiers created afterwards. Operators must accurately describe their actual retention period, purpose, lawful-basis assessment, and review or objection route in their own privacy notice.

## Privacy and account deletion

Deleting a normal account does not create a registration-blocking identifier. Deleting an account while it is suspended creates only a keyed digest of the normalized email address, its algorithm version, and creation and expiry timestamps. The collection does not retain the clear-text email address, user ID, suspension reason, or IP address.

The digest is pseudonymous rather than anonymous data. The bundled wording describes an operator's possible legitimate-interests assessment in measured terms and is an effort to improve transparency and applicable UK GDPR practice. It is not legal advice, a compliance certification, or a guarantee of compliance.

## Rollback

The self-host upgrade command creates a database backup and automatically restores the previous image and data if migration, health, or integrity checks fail. For a manual rollback after a successful migration, restore the matching pre-upgrade PocketBase backup and previous immutable image together. Reverting only the image leaves the migrated schema and acknowledgement state in place.

Project-operated deployments must additionally coordinate the reviewed instance privacy notice, legal acknowledgement version, application revision, and their matching backup and rollback artifacts.
